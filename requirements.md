# Todo App E2E Requirements

This list describes the functionality currently available in the Todo app.
Each requirement is written as an observable behavior that can be turned into
an end-to-end test.

## Test setup and test data

- The application is available at `http://localhost:5173`.
- Each test that depends on an empty list must clear the browser local storage
  key `todo_tasks_v1` before loading or reloading the application.
- A task has a topic, priority, status, description, completion state, and
  timestamps. The task ID is generated by the application.
- Tests should use unique task topics so that individual task cards can be
  selected reliably.

## Application availability

- **REQ-APP-001:** Opening `/` displays the Todo application, including the
  task form and the task list.
- **REQ-APP-002:** Requesting `/health` returns JSON with `status` equal to
  `ok`.
- **REQ-APP-003:** Requesting `/version` returns JSON identifying the
  application as `todo-training-app` and version `0.1.0`.

## Initial state and form

- **REQ-FORM-001:** With no stored tasks, the task list is empty and the
  message `No tasks yet. Add your first task above.` is visible.
- **REQ-FORM-002:** The form is in create mode initially. Its heading is
  `Create Task` and its submit button says `Save Task`.
- **REQ-FORM-003:** The topic field is required and accepts at most 120
  characters.
- **REQ-FORM-004:** The priority field is required and offers `Low`,
  `Medium`, and `High`. `Medium` is selected by default.
- **REQ-FORM-005:** The status field is required and offers `To do`,
  `In progress`, `Blocked`, and `Done`. `To do` is selected by default.
- **REQ-FORM-006:** The description field is optional and accepts free-form
  text.
- **REQ-FORM-007:** Clicking `Reset` clears the current form values, returns
  the form to create mode, restores priority `Medium` and status `To do`, and
  changes the submit button back to `Save Task`.
- **REQ-FORM-008:** Submitting without a topic does not create a task and
  keeps the topic field focused.
- **REQ-FORM-009:** Leading and trailing whitespace is removed from topic and
  description values when they are saved.

## Creating tasks

- **REQ-CREATE-001:** A valid topic can be saved as a new task.
- **REQ-CREATE-002:** The saved task displays its topic and description in the
  task list.
- **REQ-CREATE-003:** The saved task displays its selected priority as a
  `Low`, `Medium`, or `High` badge.
- **REQ-CREATE-004:** The saved task displays its selected status as `To do`,
  `In progress`, `Blocked`, or `Done`.
- **REQ-CREATE-005:** Creating a task with status `Done` marks it completed
  immediately; it is rendered as completed and appears after incomplete
  tasks.
- **REQ-CREATE-006:** After a successful save, the form resets to create mode
  and the new task remains visible in the list.
- **REQ-CREATE-007:** Task data survives a page reload because it is persisted
  under local storage key `todo_tasks_v1`.

## Listing and ordering

- **REQ-LIST-001:** Every task card provides `Edit`, `Complete`/`Undo`, and
  `Delete` controls.
- **REQ-LIST-002:** Incomplete tasks appear before completed tasks.
- **REQ-LIST-003:** Within the same completion group, higher-priority tasks
  appear before lower-priority tasks in this order: High, Medium, Low.
- **REQ-LIST-004:** Tasks with equal completion and priority are ordered from
  newest to oldest.
- **REQ-LIST-005:** A completed task is visually distinguished from an
  incomplete task, including reduced opacity and a struck-through topic.
- **REQ-LIST-006:** User-provided topic and description text is displayed as
  text rather than interpreted as HTML.

## Editing tasks

- **REQ-EDIT-001:** Clicking `Edit` loads the selected task's topic, priority,
  status, and description into the form.
- **REQ-EDIT-002:** Entering edit mode changes the form heading to `Edit Task`
  and the submit button to `Update Task`.
- **REQ-EDIT-003:** Saving an edited task updates that task instead of creating
  a second task.
- **REQ-EDIT-004:** Editing persists the changed topic, priority, status, and
  description in the task card.
- **REQ-EDIT-005:** Editing a task updates its modification timestamp while
  retaining its task identity and creation timestamp.
- **REQ-EDIT-006:** Changing an existing task's status to `Done` marks it
  completed.
- **REQ-EDIT-007:** Changing a completed task to another status does not
  automatically clear its completed state; the task can be made incomplete
  through the `Undo` control.
- **REQ-EDIT-008:** Clicking `Reset` while editing exits edit mode without
  saving unsaved changes.

## Completing and undoing tasks

- **REQ-COMPLETE-001:** Clicking `Complete` marks an incomplete task as
  completed, changes its status to `Done`, and changes the control label to
  `Undo`.
- **REQ-COMPLETE-002:** Completing a task moves it behind incomplete tasks
  according to the list ordering rules.
- **REQ-COMPLETE-003:** Clicking `Undo` on a completed task marks it
  incomplete, changes a `Done` status back to `To do`, and changes the control
  label to `Complete`.
- **REQ-COMPLETE-004:** Undoing a task with a non-`Done` status preserves that
  status while clearing its completed state.
- **REQ-COMPLETE-005:** Completion changes are persisted and remain after a
  page reload.

## Deleting tasks

- **REQ-DELETE-001:** Clicking `Delete` asks the user to confirm with the
  message `Delete this task?`.
- **REQ-DELETE-002:** Confirming deletion removes only the selected task from
  the list and local storage.
- **REQ-DELETE-003:** Cancelling the confirmation leaves the selected task
  unchanged.
- **REQ-DELETE-004:** Deleting the final task restores the empty-list message.
- **REQ-DELETE-005:** A deleted task does not reappear after a page reload.

## Suggested E2E scenarios

The following scenarios provide a practical first Cypress suite:

1. Load the app with empty storage and verify the initial form and empty state.
2. Create a task using each priority and each status.
3. Verify required topic validation and the 120-character limit.
4. Verify whitespace trimming and optional description handling.
5. Create tasks with mixed priorities and completion states; verify ordering.
6. Reload the page and verify task persistence.
7. Edit every task field and verify that no duplicate task is created.
8. Reset a filled create form and reset an edit form with unsaved changes.
9. Complete an incomplete task, verify its status/order/control label, then undo
   it.
10. Delete a task after accepting the confirmation.
11. Delete a task after cancelling the confirmation.
12. Enter HTML-looking text in topic and description and verify it is rendered
    literally.
13. Check the `/health` and `/version` endpoints.
